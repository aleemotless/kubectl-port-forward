Kubernetes networking · kubectl

kubectl port-forwardA private tunnel from localhost into one Pod.

Your Pod has no public address, and you don't want to give it one just to poke at it. Port-forward borrows the connection you already have to the API server and threads a TCP tunnel through it, all the way into the Pod's network namespace.

  • TCP only
  • binds 127.0.0.1 by default
  • targets one Pod
  • lives as long as the command

    Anatomy of the command
    
    
    Read it left to right: where, what, and which two ports
    
  
    
  
    
    
    
      kubectl port-forward
      -n default
      pod/nginx-pod1
      8080:80
      --address 127.0.0.1
    
    
    
      
      
    • kubectl port-forward
      Runs in the foreground. The tunnel exists only while this process does; Ctrl-C closes it.
      • 
      
    • -n default
      Namespace of the target. Leave it out and kubectl uses your current context's namespace.
      • 
      
    • pod/nginx-pod1
      The target. deploy/, rs/, sts/ and svc/ work too, but kubectl resolves them to a single Pod first.
      • 
      
    • 8080 local port
      Opened on your machine. Write :80 to get a random free port, or just 80 to use the same number on both sides.
      • 
      
    • 80 remote port
      The port inside the Pod: your containerPort. With svc/, it is the Service port, which kubectl maps to the targetPort.
      • 
      
    • --address
      Which local interfaces to bind. The default localhost means 127.0.0.1 and ::1, so only you can connect. 0.0.0.0 opens it to your network.
      • 
    
    
  
    

    



    
  
    
    
    
      
    Inside the pipe
    
      
    One tunnel, many streams
    
      
    kubectl dials the API server once. Every TCP connection you open to localhost:8080 becomes a new pair of streams inside that single connection:
    
      
    data carries your bytes in both directions. error is a side channel where the Pod's end reports problems such as "connection refused".
    
      
    Each stream carries headers that name the remote port and a requestID, so the far side can keep the conversations apart. Add connections to see them pile up.
    
    
    
    
    
      
    
        
      
    
      
    
        
        
      
    
      
    
    
    
  
    

    



    
  
    
    
    The Service trap
    
    
    svc/web does not mean load balancing
    
    
    When you forward to a Service, kubectl only uses it as a lookup. It reads the selector, picks one running Pod, and tunnels straight to it. kube-proxy and the ClusterIP never see your traffic. Compare that with how traffic reaches a Service from inside the cluster, then delete the Pod that's serving.
    
  
    
  
    
    
    
      
    
    
    
    
      
    
        
        
      
    
      
      
      
    
    
    
    
  
    
  
    Port-forward is a debugging tool, not an exposure method. If the Pod restarts, gets rescheduled, or is replaced by a rollout, kubectl prints lost connection to pod and exits. It never reconnects on its own.
    

    



    
  
    
    
    Forwarding to a Deployment
    
    
    deploy/nginx-deployment still ends at one Pod
    
    
    Your deploy.yml asks for 3 replicas. kubectl walks from the Deployment to its selector, lists the matching Pods, picks one running Pod, and opens the tunnel to that Pod by name. The Deployment and ReplicaSet never carry a byte. The manifest declares no containerPort, and port-forward doesn't need one: it dials port 80 inside the Pod directly.
    
  
    
  
    
    
    
      
    
    
    
    
      
      
      
      
    
    
    
    
  
    
  
    Scaling up, rolling out a new image, or kubectl rollout restart all replace Pods. The forward stays pinned to the Pod it picked at start, so the first time that Pod is terminated, kubectl exits.

      Troubleshooting
      
    
      The errors you'll actually see
      
  
      
  
      
    
      
      
      Local port already taken
      

      Unable to listen on port 8080: Listeners failed to create with the following errors: [unable to create listener: Error listen tcp4 127.0.0.1:8080: bind: address already in use]
error: unable to listen on any of the requested ports: [{8080 80}]
      
      
      Fix: something else owns 8080 on your machine. Pick another local port (9090:80) or find the culprit with lsof -i :8080.
      
    
      
    
      
      
      Nothing listening inside the Pod
      

      an error occurred forwarding 8080 -> 80: error forwarding port 80 to pod …: failed to connect to localhost:80 inside namespace …: connect: connection refused
      
      
      Fix: the tunnel works, the app doesn't. The remote port is wrong or the process hasn't started. Check with kubectl logs and the containerPort.
      
    
      
    
      
      
      Forbidden by RBAC
      

      error: error upgrading connection: pods "nginx-pod1" is forbidden: User "dev" cannot create resource "pods/portforward" in API group "" in the namespace "default"
      
      
      Fix: grant create on pods/portforward, plus get on pods. Test with kubectl auth can-i create pods/portforward.
      
    
      
    
      
      
      Pod went away
      

      Handling connection for 8080
error: lost connection to pod
      
      
      Fix: the Pod restarted, was evicted, or a rollout replaced it. Run the command again. For a long-lived loop, wrap it: while true; do kubectl port-forward …; sleep 1; done.

      Cheat sheet
      
    
      Commands worth keeping
      
  
      
  
      
    
      Forward to the Pod from pod.yaml
      kubectl port-forward pod/nginx-pod1 8080:80
      
    
      Let kubectl choose a free local port
      kubectl port-forward pod/nginx-pod1 :80
      
    
      Several ports in one tunnel
      kubectl port-forward pod/nginx-pod1 8080:80 8443:443
      
    
      Reach a database in another namespace
      kubectl port-forward -n db svc/postgres 5432:5432
      
    
      Share with your LAN (careful)
      kubectl port-forward --address 0.0.0.0 pod/nginx-pod1 8080:80
      
    
      Run it in the background, stop it later
      kubectl port-forward pod/nginx-pod1 8080:80 >/dev/null 2>&1 &
kill %1
      
  
      

      


      
  Request path and stream behavior follow upstream Kubernetes: kubectl 1.31+ speaks WebSocket to the API server by default (older clusters fall back to SPDY). Port-forward carries TCP only; UDP is not supported.
